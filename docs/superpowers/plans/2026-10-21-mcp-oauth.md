# MCP OAuth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Connect normal ChatGPT Plus and Zapia through OAuth with owner-only email PIN authentication.

**Architecture:** One existing Worker combines authorization and resource roles through the official OAuthProvider. Cloudflare Access OIDC authenticates the owner; the provider manages client registration, consent state, codes and tokens in an exclusive KV binding. Existing stateless read-only MCP tools remain behind verified identity and scope checks.

**Tech Stack:** Existing TypeScript / Workers / MCP v2; workers-oauth-provider 1.2.3; jose 6.2.13 (stable versions verified in npm).

**Spec:** docs/superpowers/specs/2026-10-21-mcp-oauth-design.md

## Global Constraints

- Canonical resource: https://elo-agendor-mcp.example.workers.dev/mcp
- Only owner@elo.example may authorize or use CRM access.
- Preserve eight read-only tools, CRM shared budget, cancellation and validation.
- Access uses OIDC and One-time PIN, exact callback /callback; no secrets in Git, arguments or logs.
- Require crm:read, S256, valid audience and browser-bound consent. Support offline_access for renewal.
- Production /mcp never falls back to MCP_TEST_TOKEN. Agendor Chat stays blocked.
- KV consistency does not imply immediate global revocation or atomic state consumption.
- Preserve unrelated untracked pnpm files. User explicitly requested implementation after reviewing design; execute inline without further planning approval prompts.

## Review Focus

- A forged/expired OIDC token or different email must never create a grant (Task 1).
- A modified approval form, callback in another browser, or malicious client metadata must not authorize a different client (Task 2).
- Missing configuration must never fall back to the old static token (Task 3).
- Refresh/revocation for one client must preserve a different client's grant (Task 3).
- Account onboarding or PIN may require the user, but implementation and local verification must continue independently (Task 4).
