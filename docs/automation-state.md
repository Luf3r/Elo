# Automation account storage

`accountState(env)` always resolves the server-owned `elotenant` Durable Object. HTTP callers cannot choose the account or obtain a generic budget endpoint. Before activating automation, the server must verify CRM and Chat account identities and call `activate` with those IDs. A mismatch fails with `ACCOUNT_RECONFIGURATION_REQUIRED`; credentials must not silently reuse another account's memory. Changing accounts requires explicit operator reconfiguration, not an automatic reset.

SQLite migration 1 creates the workflow tables atomically and records its version. New migrations must be appended rather than editing an applied migration. All reservation/CAS operations use short `transactionSync` blocks. Hash computation and network I/O remain outside those blocks. Leases last 600 seconds, bind user/client/work, and use monotonic per-target fences. A renewed lease invalidates its old manifest and derived claims. Command reservations return `busy` for a second dispatcher; abandoned requests become `uncertain` and are never automatically reissued. Completion requires the matching operation, version, fence and live lease.

Persistent work/command deduplication contains IDs, fingerprints and receipts, never bearer tokens or command payloads. Snapshot manifests store IDs, revisions, direction, coverage and hashes only. Bounded server-produced plan/context evidence may contain customer fields for at most 90 days. Reads fail closed after expiry; alarms target the earliest evidence expiry and startup cleanup removes expired data. Deduplication tombstones and verified entity links remain while the integration is active. Phone observations, if added by later identity code, must be hashed references or bounded evidence, never a unique person binding or indefinite raw phone storage. Context projection/identity writers and queue interpretation belong to subsequent tasks. `AuthorizedPlan` is not persisted or reconstructed here; downstream execution must preserve and enforce its original `validUntil` and copied actor grants.

CRM and Chat adapters reserve their product's shared rolling budget immediately before each real upstream request, including internal reads and attachment downloads. Four reservations are allowed per 10,000 milliseconds. The fifth returns `retryAt`; canceled reservations are not refunded. Missing/unavailable budget fails closed, and MCP wrappers do not charge separately. Adapter unit tests use an explicit synthetic `budgetGate`; production factories use the account Durable Object. Only MCP/OAuth ingress retain native per-client/IP rate limiters.

The standalone discovery CLI remains disabled before credentials/network because it has no authenticated fixed Worker route into this shared budget. No local delay or unauthenticated budget endpoint substitutes for coordination. Live contract probes likewise receive no bypass gate; do not add one merely to run them locally.

Runtime tests use the installed Cloudflare Vitest plugin, actual SQLite storage and `evictDurableObject`. Expected domain errors are caught inside `runInDurableObject` because plugin 1.4.6 duplicates rejected RPC promises as unhandled errors. Positive/concurrent calls and restart checks use normal RPC.

`PlanBasis` and command reservations require the server-resolved `customerId`. The first valid plan/projection transaction binds each work item immutably to that customer in `work_customers`; another conversation may bind to the same customer. Saving a plan and authorizing a first command dispatch compare the basis with the customer's current context version inside the transaction. A context refresh invalidates every associated customer's plan, so a different conversation cannot dispatch an obsolete proposal. Existing command tombstones remain queryable for the same customer without granting a new dispatch.

Migration 3 creates those associations, recovers unambiguous associations from existing context ownership, and invalidates older plans/projections that lack the new basis. Existing contexts and command receipts remain intact. Refreshes collect confirmed and uncertain receipts across all associated work, preserving commercial history. A previously rendered projection may be replaced by newly reconciled work; an unpublished projection continues to reserve the pending context version against competing overwrites.

Migration 4 also recovers missing legacy associations from the stored server-generated work lease when its explicit customer target is valid and matches the work ID. This covers confirmed/uncertain command tombstones created before any context was published. It does not infer identity from a conversation, a new caller argument, malformed leases or conflicting context ownership, and does not overwrite existing associations.
